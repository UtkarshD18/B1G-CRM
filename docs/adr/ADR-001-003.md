# B1GCRM Architectural Decision Records (ADRs)

This directory documents the structural architectural decisions made for B1GCRM, capturing the context, evidence, and justifications behind each layout choice.

---

## ADR-001: Strict Layered Architecture Boundary

- **Status:** Approved
- **Context:** The legacy codebase mixed database execution directly within express router definition blocks, resulting in poor testability and high cross-routing files coupling.
- **Decision:** Establish a strict, unidirectional data boundary: `Routes → Controllers → Services → Helpers → Database/APIs`.
- **Consequences:** Controllers handle HTTP parameter validation and response structuring only. Services manage business logic, workflows, and query orchestration. No raw SQL or controllers are imported backwards.

---

## ADR-002: Bounded Domain Table Write Ownership

- **Status:** Approved
- **Context:** Shared mutations on central database tables (e.g. `plan` and `user`) from multiple routes made updates risky, causing regression bugs on user plan expired events.
- **Decision:** Bind each database table to a single write-owner service. Only the service designated as the table owner may execute write operations (`INSERT`, `UPDATE`, `DELETE`) on it.
- **Consequences:** Other domains should not perform writes directly to tables they do not own. Shared write logic should remain encapsulated within the owning domain (e.g. by using shared transactional helper functions or coordinating via specialized helpers), preventing ad hoc mutations.

---

## ADR-003: Rejection of Repository Layer Pattern

- **Status:** Approved
- **Context:** We evaluated introducing a persistence boundary (Repositories) separating database queries from Services.
- **Decision:** Explicitly **rejected** the Repository layer.
- **Evidence:** Codebase SQL audit scanned 1,140 SQL-containing lines and verified the cross-service query duplication rate is below 3%.
- **Justification:** Adding an extra repository abstraction layer provides little maintenance benefit and introduces unnecessary file boilerplate for simple CRUD persistence queries. We prefer direct service query inline execution.
